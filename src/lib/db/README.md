# Internal database (SQLite, raw SQL)

The project's own data store — workspaces, users, database connections, schema
metadata, instructions, agents, chat, suggestions, logs, etc. Embedded SQLite via
**better-sqlite3**, running in-process in the **same container as the
mysql-runner**. This is **not** the customer databases the
[mysql-runner](../mysql-runner/README.md) connects to.

The schema is plain SQL, generated by a builder from declarative table specs — no
ORM.

## Layout

| Path | Role |
| --- | --- |
| `schema/tables.ts` | **Source of truth** — declarative specs for every table. Edit here. |
| `schema/dsl.ts` | Tiny DSL + SQL emitter used by the builder. |
| `build-schema.ts` | Builder — compiles specs → `schema.sql`. |
| `schema.sql` | **Generated** DDL (committed). Applied at startup. |
| `client.ts` | better-sqlite3 singleton; applies `schema.sql` on first open. |
| `crypto.ts` | AES-256-GCM for `*_enc` secret columns. |
| `repositories/` | Typed data access (the only way app code touches the DB). |
| `../../types/db.ts` | Shared row types mirroring the schema. |

## Build the schema

Edit `schema/tables.ts`, then:

```bash
npm run db:build            # regenerate src/lib/db/schema.sql
npm run db:build -- --apply # regenerate AND apply (additive: CREATE IF NOT EXISTS)
npm run db:build -- --reset # regenerate AND REBUILD the db (drops + recreates; loses data)
npm run test:internal-db    # end-to-end smoke test (uses a temp db)
```

The app also applies `schema.sql` automatically on first DB access (`client.ts`),
and every statement is `CREATE ... IF NOT EXISTS`, so `--apply` is safe to run
repeatedly. **`--apply` cannot alter existing tables** (changed columns won't take
effect) — during schema iteration use `--reset` to rebuild from scratch. A proper
migration tool can be added later when there's data to preserve.

## Tables

`users`, `roles`, `user_roles`, `workspaces`, `databases`, `db_tables`,
`db_columns`, `instructions`, `env_keys`, `agents`, `chat`, `chat_messages`,
`suggestions`, `metadata`, `query_rules`, `user_logs`, `system_logs`.

Conventions: `INTEGER PRIMARY KEY AUTOINCREMENT` ids, `TEXT` timestamps defaulting
to `CURRENT_TIMESTAMP` with an `updated_at` trigger, enums as `CHECK (col IN (...))`,
booleans as `0/1` integers, secrets in `*_enc` columns, foreign keys with
`ON DELETE` actions.

## Usage (repositories)

```ts
import {
  workspacesRepository,
  usersRepository,
  rolesRepository,
  userRolesRepository,
  databasesRepository,
  userLogsRepository,
} from "@/lib/db";

const ws = workspacesRepository.create({ name: "AllEvents", slug: "allevents" });
const user = usersRepository.create({ username: "mihir", email: "a@b.com", password: hash });
const role = rolesRepository.create({ name: "owner", permissions: { "*": true } });
userRolesRepository.assign(user.id, role.id, { databases: ["read", "write"] });

// Store a DB connection (secrets encrypted automatically)
const conn = databasesRepository.create({
  workspaceId: ws.id, name: "replica",
  host: "replica.internal", username: "app", password: "secret",
  connectionMethod: "ssh", sshHost: "bastion", sshUsername: "ubuntu",
  sshAuthMethod: "privateKey", sshPrivateKey: pem,
});

// Bridge a stored connection straight into the mysql-runner
import { runQuery } from "@/lib/mysql-runner";
const opts = databasesRepository.toRunnerOptions(conn.id); // decrypts secrets
await runQuery({ ...opts, query: "SELECT 1", readOnly: true });
```

`list()` / `getSafe()` never return secrets (they expose `has_password` /
`has_ssh_secret` booleans). Only `toRunnerOptions()` decrypts.

Repositories currently exist for the core entities (workspaces, users, databases,
logs); add more in `repositories/` as features need them — every table already
exists in the schema.

## Configuration

| Env var | Default | Purpose |
| --- | --- | --- |
| `DATABASE_PATH` | `.data/app.db` | SQLite file location (gitignored). |
| `APP_ENCRYPTION_KEY` | _(required for secrets)_ | 32-byte key (hex/base64) for `*_enc` fields. |

Generate a key: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`

## Docker note

`schema.sql` and a writable `.data/` (or a mounted volume) must be present at
runtime. better-sqlite3 is a native addon — on `node:*-alpine` it may need build
tools; `node:22-slim`/`bookworm` use the prebuilt binary out of the box.
`next.config.ts` lists it in `serverExternalPackages` so it isn't bundled.
